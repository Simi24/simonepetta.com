4.1 Provisioning dell’Infrastruttura tramite Terraform

L’adozione di un approccio Infrastructure as Code (IaC) garantisce la riproducibilità, la tracciabilità e la coerenza degli ambienti cloud. Il repository oggetto di questa sezione traduce la topologia cloud, descritta nei capitoli precedenti, in codice HCL (HashiCorp Configuration Language), il linguaggio dichiarativo utilizzato da Terraform per definire risorse infrastrutturali. Ogni componente trova una corrispondenza diretta in moduli Terraform versionati e organizzati secondo una struttura gerarchica.

Come discusso nel Capitolo 3, la scelta di Terraform come strumento di provisioning deriva da tre fattori tecnici: la natura dichiarativa del linguaggio, che delega al motore il calcolo del piano di esecuzione; il supporto multi-provider, essenziale per gestire risorse AWS, Google Cloud Platform e MongoDB Atlas in un singolo repository; e l’ecosistema di moduli riutilizzabili.

La gestione dello stato per ambienti multipli richiede l’utilizzo di Terragrunt come orchestratore. Terragrunt opera come wrapper per Terraform, aggiungendo funzionalità di gestione dello stato remoto, generazione automatica di file di configurazione e risoluzione delle dipendenze tra moduli [37]. Questa combinazione applica il principio Don’t Repeat Yourself alla definizione dell’infrastruttura.

La struttura logica di questa sezione segue il flusso di astrazione dell’infrastruttura: la scomposizione iniziale del repository illustra la separazione tra configurazione e implementazione; le sezioni successive dettagliano l’orchestrazione dello stato, la segregazione degli ambienti (multi-account) e, infine, la logica interna dei moduli riutilizzabili sviluppati per la piattaforma.

4.1.2 Orchestrazione con Terragrunt

Terragrunt introduce un livello di astrazione che risolve la configurazione del backend remoto, la generazione dei file provider e la gestione delle dipendenze tra moduli.

Gestione dello Stato Remoto e Provider

Lo stato di Terraform contiene la mappatura tra le risorse dichiarate nel codice e quelle allocate nel cloud. Per garantire persistenza, cifratura server-side e mutua esclusione durante le operazioni concorrenti, il repository utilizza un backend Amazon S3 con meccanismo di lock affidato ad Amazon DynamoDB.

Terragrunt genera automaticamente il file provider.tf per ogni modulo. La piattaforma richiede tre provider AWS distinti e un provider Google Cloud per gestire risorse eterogenee.

Gerarchia di Inclusione e Dipendenze

Ogni modulo in un ambiente specifico è rappresentato da un file terragrunt.hcl che combina la configurazione globale con il template del modulo e le dipendenze specifiche. Questa composizione a tre livelli (root, template, ambiente) centralizza la logica. Ad esempio, il blocco dependency consente di estrapolare gli output di un modulo già applicato (es. l’infrastruttura di messaggistica) e passarli come input al modulo corrente (es. i microservizi).

4.1.3 Architettura Multi-Account

La piattaforma opera su un’organizzazione AWS composta da ambienti segregati (dev, prod, shared), la cui topologia è schematizzata in Figura 8. L’utilizzo del servizio AWS Organizations permette di istanziare account separati, assegnando indirizzi email univoci e ruoli amministrativi per l’assunzione di identità cross-account.

L’accesso degli operatori è regolato tramite IAM Identity Center. Il modulo definisce gruppi e permission set specifici; ad esempio, il gruppo assegnato all’analisi dati riceve esclusivamente i permessi di lettura per interrogare il data warehouse tramite Amazon Athena, senza facoltà di modifica sulle risorse.

4.1.4 Moduli Riutilizzabili

La directory utils/modules/ contiene i moduli Terraform che incapsulano i pattern architetturali ricorrenti.

Modulo api-gateway-lambda

Questo modulo rappresenta il pattern standard per il deployment dei microservizi serverless. Crea un endpoint HTTP (API Gateway v2), una funzione Lambda, un authorizer JWT [22] opzionale basato su Amazon Cognito e i relativi gruppi di log in CloudWatch.

Un aspetto ingegneristico rilevante risiede nella separazione tra il ciclo di vita dell’infrastruttura e quello del codice applicativo. Nel blocco di definizione della funzione Lambda, l’attributo image_uri viene escluso dal monitoraggio dello stato di Terraform:

resource "aws_lambda_function" "lambda" {
  function_name = "${var.name}-${var.env}"
  role          = aws_iam_role.lambda_assume_role.arn
  package_type  = "Image"
  image_uri     = var.app_image

  lifecycle {
    ignore_changes = [image_uri]
  }

  timeout       = var.lambda_timeout
  memory_size   = var.lambda_memory_size
  architectures = ["arm64"]

  environment {
    variables = merge(
      var.environments,
      {
        CLOUD_ENV = var.env
        STAGE     = "/api"
    })
  }
}

Questa direttiva impedisce a Terraform di ripristinare una versione precedente dell’immagine Docker qualora l’applicazione sia stata aggiornata in modo asincrono dalle pipeline di Continuous Deployment. La policy IAM della funzione viene costruita dinamicamente componendo i permessi di base (scrittura dei log) con istruzioni opzionali passate dal modulo chiamante, consentendo un’applicazione granulare del principio del minimo privilegio.

Modulo datasource-etl

Questo modulo definisce la pipeline ETL (Extract, Transform, Load) per l’ingestione dei dati. L’architettura di questo componente, dettagliata in Figura 9, prevede una netta separazione fisica e logica dei dati: un prefisso S3 raw/ per i dati grezzi e un prefisso clean/ per i dati trasformati in formato Apache Parquet.

L’orchestrazione si divide in due fasi computazionali. La fase di estrazione (Extractor) utilizza una funzione Lambda invocata temporalmente tramite regole Amazon EventBridge. Per evitare la duplicazione dei dati grezzi in caso di errori temporanei della sorgente, i retry automatici dell’invocazione asincrona sono disabilitati (maximum_retry_attempts = 0).

La fase di trasformazione è puramente event-driven: viene attivata dalle notifiche S3 alla creazione di un nuovo oggetto nel prefisso raw/. Le policy IAM dei due componenti riflettono il flusso dei dati: l’Extractor ha permessi di sola scrittura su raw/, mentre il Transformer legge da raw/ e scrive esclusivamente su clean/.

I dati elaborati vengono resi interrogabili tramite l’integrazione con AWS Glue Catalog e Amazon Athena. Il modulo implementa la funzionalità di Partition Projection per ottimizzare le query; le partizioni temporali (anno, mese, giorno) vengono calcolate matematicamente dal motore di Athena in base a range predefiniti, eliminando la necessità di eseguire operazioni di scansione sincrona (crawler) sui bucket S3.

4.1.5 Risorse Condivise e Continuous Integration

L’account condiviso ospita i repository Elastic Container Registry (ECR). L’accesso da parte dei sistemi di Continuous Integration (GitHub Actions) avviene senza lo scambio di credenziali, sfruttando il protocollo OIDC (OpenID Connect). Il provider di identità assume un ruolo IAM temporaneo che garantisce unicamente i permessi di push sui repository di destinazione.

4.1.6 Strategia di Tagging

Ogni risorsa gestita tramite IaC riceve un set di tag obbligatori (terraform, environment, project, subproject). Oltre all’identificazione visiva, questi metadati sono integrati con AWS Cost Explorer come Cost Allocation Tags, permettendo l’analisi e la ripartizione dei costi infrastrutturali per specifico dominio funzionale o ambiente.

4.2 Sviluppo del Flusso ETL Event-Driven

Questa sezione dettaglia l’implementazione applicativa della pipeline di ingestione dati. L’analisi procede seguendo il ciclo di vita dell’evento asincrono: l’inizializzazione e validazione del payload di estrazione, l’instradamento dinamico verso i moduli di integrazione esterni e, infine, la trasformazione del dato in memoria con conseguente serializzazione nel formato colonnare Parquet. La logica software è progettata per operare all’interno dei limiti computazionali ed effimeri del runtime serverless descritto nel Capitolo 3.

4.2.1 Logica Applicativa di Estrazione

L’estrattore ETL opera come un componente senza stato che interroga una sorgente esterna per produrre dati grezzi in risposta a un evento asincrono. Per standardizzare lo sviluppo ed evitare la duplicazione del codice tra i vari microservizi, il sistema integra un repository condiviso importato come submodule Git [48]. Questo modulo isola il codice infrastrutturale di base, offrendo un livello di astrazione per l’interazione con le risorse cloud e permettendo all’estrattore di concentrarsi unicamente sulla logica di recupero dati.

L’innesco del processo avviene tramite un payload JSON strutturato, il quale definisce il contesto dell’operazione. Il contratto dei dati prevede quattro parametri essenziali: l’identificativo del servizio da interrogare (service), la finestra temporale dell’estrazione, una chiave di partizionamento (iterator) per supportare esecuzioni parallele in ambienti multi-tenant, e i metadati per il tracciamento distribuito.

La validazione a runtime del payload è demandata alla libreria Pydantic. L’istanziamento rigoroso del modello dati, mostrato nel Listato 4.1, implementa un meccanismo di interruzione rapida (fail-fast): il sistema scarta istantaneamente le richieste malformate prima di allocare risorse o inizializzare connessioni di rete verso i provider esterni.

Il controllo del flusso interno all’estrattore impiega un meccanismo di instradamento basato sul parametro service. Per rispettare il principio Open/Closed e garantire l’estensibilità della piattaforma, l’architettura adotta il pattern architetturale Registry. Questo schema, illustrato nel Listato 4.2, mappa in modo statico ogni servizio esterno alla propria funzione di estrazione dedicata, eliminando la necessità di costrutti condizionali centralizzati (anti-pattern spesso riscontrabile in architetture monolitiche).

L’aggiunta di una nuova sorgente dati risulta perciò un’operazione circoscritta: l’ingegnere implementa la specifica logica di chiamata HTTP e la annota con il decoratore ServiceRegistry.register("nome_servizio"). L’applicativo carica questi moduli dinamicamente durante la fase di avvio del runtime (cold start), abilitando un comportamento strettamente modulare.

La robustezza dell’estrattore è garantita da ulteriori decoratori applicativi, sviluppati per uniformare la gestione delle anomalie di rete. Il sistema classifica le eccezioni in errori temporanei (es. rate limit, latenze del server remoto), che giustificano un successivo ritentativo, ed errori fatali (es. permessi mancanti), che interrompono definitivamente l’esecuzione. Il Listato 4.3 mostra come il decoratore isoli l’esecuzione del gestore, traducendo le eccezioni generiche in classi di errore di dominio per il corretto instradamento verso l’infrastruttura di scarto (Dead Letter Queue).

Al termine dell’elaborazione in memoria, l’estrattore finalizza il processo confinando il payload grezzo ottenuto nel livello di archiviazione persistente. L’estrattore salva il file all’interno del prefisso raw/ del bucket di destinazione, utilizzando una chiave deterministica contenente il nome del servizio utilizzato per l’estrazione basata sui parametri del payload originale. Una volta confermata la scrittura remota, la funzione termina l’esecuzione, concludendo il ciclo vitale del worker e innescando, a livello infrastrutturale, l’evento per la successiva fase di trasformazione.

4.2.2 Trasformazione del Dato e Serializzazione in Parquet

Il componente di trasformazione esegue l’elaborazione dei dati grezzi estratti nella fase precedente. L’inserimento di un nuovo file nel percorso raw/ del bucket Amazon S3 genera un evento asincrono che innesca automaticamente l’esecuzione della funzione AWS Lambda. L’handler della funzione intercetta il payload dell’evento, estrae la chiave identificativa dell’oggetto S3 e procede al download del file grezzo nell’ambiente di esecuzione temporaneo (/tmp). Una volta caricato in memoria, il software applica le logiche di pulizia, valida lo schema dei dati e serializza le informazioni nel formato colonnare Parquet, archiviando infine il risultato nel percorso clean/ del Data Lake.

L’adozione della libreria Python Polars [51] per la manipolazione dei dati in memoria è motivata da tre fattori principali. Il primo fattore riguarda l’efficienza delle operazioni di I/O: l’utilizzo di un motore di esecuzione interno ottimizzato riduce la pressione sulla memoria allocata, mitigando le restrizioni intrinseche ai runtime effimeri come AWS Lambda. Il secondo fattore concerne la tipizzazione esplicita: Polars applica un cast rigoroso verso tipi di dato primitivi (quali interi a 64 bit o timestamp), uniformando in modo deterministico le discrepanze presenti nei set di dati JSON in ingresso. Il terzo fattore è la disponibilità di trasformazioni vettoriali, le quali permettono di eseguire operazioni di validazione e manipolazione su intere colonne simultaneamente, ottimizzando i tempi di esecuzione rispetto a un’iterazione procedurale.

Per orchestrare le molteplici varianti strutturali dei formati in ingresso, l’architettura implementa un costrutto logico che combina il pattern Factory con un registro statico. Ogni classe concreta, dedicata a una specifica strategia di trasformazione, dichiara la propria registrazione tramite un decoratore sintattico, associandosi a una stringa identificativa univoca. Durante l’elaborazione, il sistema ispeziona la configurazione per estrarre la chiave di instradamento e istanzia dinamicamente la classe corretta. Questo design, illustrato nel Listato 4.5, separa il contratto di base dalle implementazioni specifiche di dominio, eliminando i costrutti condizionali monolitici e agevolando l’estensione del codice.

Il processo di sanificazione dei dati si articola su due livelli logici distinti. Il primo livello, incapsulato all’interno della classe astratta di base, applica le regole di validazione comuni a tutti i flussi operativi. La classe base esegue la rimozione degli spazi bianchi superflui (trimming) su tutte le stringhe e normalizza i token testuali anomali, convertendoli nel tipo nullo nativo del linguaggio. Il codice gestisce inoltre l’adeguamento delle unità di misura, come la conversione di valori finanziari in micro-unità tramite divisione scalare, e forza la standardizzazione dei formati temporali.

Il secondo livello di sanificazione è demandato ai trasformatori concreti, i quali gestiscono le difformità strutturali di specifici set di dati. A titolo esemplificativo, le classi specializzate eseguono la fusione di colonne separate per data e ora in un singolo timestamp, oppure applicano operazioni di flattening per convertire le strutture nidificate dei documenti JSON in schemi tabellari piatti. Al termine di questi processi di pulizia, il trasformatore formatta il DataFrame risultante in Parquet e il client delegato lo trasferisce definitivamente nella directory clean/ del bucket S3, predisponendo i dati per l’interrogazione analitica.

4.2.3 Interrogazione Analitica e Viste Materializzate in Athena

Il livello analitico del sistema si fonda su Amazon Athena e implementa una duplice strategia di interrogazione e strutturazione dei dati. La prima operazione consiste nella materializzazione fisica dei risultati all’interno del livello di archiviazione. Il processo impiega l’istruzione SQL UNLOAD per generare e depositare i dataset analitici direttamente su Amazon S3. L’operazione serializza i dati in Parquet e applica l’algoritmo di compressione Snappy [52], organizzando i file fisici secondo una gerarchia di directory basata sulle partizioni temporali (anno, mese, giorno).

La seconda operazione analitica riguarda l’accesso trasparente ai dati in continua mutazione. L’architettura adotta un pattern organizzativo che separa i dati recenti (volatili o di staging) dai dati storici consolidati (identificati come freeze). Per fornire un singolo punto di accesso logico alle applicazioni a valle, l’infrastruttura istanzia una vista virtuale unificata. Tale costrutto relazionale impiega l’operatore UNION ALL per concatenare dinamicamente le due tabelle sottostanti, schermando la complessità strutturale ai consumatori finali.

L’estrazione delle metriche di business richiede interrogazioni di aggregazione strutturate. Una delle operazioni principali riguarda il monitoraggio dell’erogazione giornaliera delle creatività pubblicitarie. Il motore Athena esegue un’interrogazione che aggrega le impressioni e i clic generati, escludendo a priori il traffico attribuibile a sistemi automatizzati (i⁢s⁢_⁢r⁢o⁢b⁢o⁢t=f⁢a⁢l⁢s⁢e). Il costrutto logico utilizza le Common Table Expressions (CTE) per pre-calcolare le metriche sulle tabelle dei fatti, eseguendo successivamente un’operazione di LEFT JOIN con le tabelle dimensionali contenenti i metadati delle campagne e dei posizionamenti.

Il calcolo del Click-Through Rate (CTR) esemplifica l’efficacia del partizionamento dei dati. La metrica è definita come il rapporto percentuale tra i clic ricevuti e le impressioni erogate:

equation (1) (1)
CTR(%)=clickimpression×100

L’estrazione di questo valore impone l’applicazione di filtri espliciti sulle colonne di partizionamento temporale. La dichiarazione esplicita dell’anno e del mese all’interno della clausola WHERE istruisce il motore di esecuzione a ignorare i dati non pertinenti alla finestra temporale analizzata.

L’implementazione di questo modello architetturale comporta quattro conseguenze dirette. In primo luogo, la combinazione del formato colonnare Parquet con la compressione Snappy ottimizza i tempi di caricamento e i costi di I/O. In secondo luogo, la clausola WHERE applicata alle partizioni temporali limita il volume di dati scansionati dal motore serverless per singola query. Il terzo aspetto riguarda la governabilità, garantita dalla segregazione logica tra le elaborazioni recenti e l’archivio storico. Infine, la definizione della vista unificata fornisce un’interfaccia stabile e disaccoppiata per i sistemi di visualizzazione e i cruscotti analitici a valle.

4.3 Implementazione dei Servizi Backend

Questa sezione analizza l’implementazione del livello applicativo sincrono, strutturata seguendo il ciclo di vita di una richiesta HTTP. L’analisi parte dal livello di instradamento, dove le richieste vengono intercettate e validate tramite iniezione delle dipendenze; prosegue illustrando il wrapper necessario all’esecuzione del framework all’interno del runtime serverless; e si conclude nel livello di persistenza, descrivendo la mappatura a oggetti per il database NoSQL e la gestione della coerenza transazionale distribuita.

4.3.1 Iniezione delle dipendenze e validazione tramite Pydantic

L’architettura dei servizi di backend sfrutta il pattern Dependency Injection per disaccoppiare la logica di business dalla risoluzione dei componenti tecnici e dalle precondizioni di dominio. Questo approccio, nativamente supportato da FastAPI, permette al sistema di eseguire controlli preliminari, quali la verifica dell’esistenza di una risorsa, l’autenticazione o il blocco di inserimenti duplicati, prima che la richiesta raggiunga il gestore principale.

Per la validazione strutturale del payload, il framework impiega la libreria Pydantic. Il processo di convalida estende il controllo statico dei tipi, integrando trasformazioni dei dati e vincoli semantici direttamente nella definizione del modello.

4.3.2 Adattamento del runtime FastAPI su AWS Lambda

L’esposizione di interfacce API sincrone tramite AWS Lambda e API Gateway impone un disaccoppiamento dei protocolli. L’implementazione utilizza l’adattatore Mangum per operare questa traduzione (da evento Lambda a standard ASGI) all’interno del codice sorgente.

4.3.3 Interazione con DynamoDB e Single Table Design in codice

Il livello di persistenza interagisce con Amazon DynamoDB applicando il pattern Single Table Design. Il sistema memorizza entità eterogenee all’interno di un’unica tabella fisica, impiegando chiavi primarie logiche e composite per definire i percorsi di accesso. Per l’interazione con il database, l’architettura adotta la libreria PynamoDB [53] in sostituzione del client standard boto3. Questa scelta ingegneristica permette di astrarre le chiamate di rete a basso livello e fornisce un Object-Document Mapper (ODM) per l’ecosistema Python. L’implementazione governa il polimorfismo applicativo definendo una classe base astratta e molteplici sottoclassi specializzate, distinte da un attributo discriminatore gestito direttamente in modo dichiarativo dalla libreria.

Per supportare schemi di interrogazione complessi senza eseguire scansioni sequenziali dispendiose, lo schema dati include Indici Secondari Globali (GSI) specializzati. Il sistema definisce un indice dedicato all’impaginazione temporale globale e un indice sparso progettato per localizzare rapidamente i record tramite identificatori generati da sistemi di terze parti.

Infine, per garantire la coerenza transazionale durante la creazione di risorse che richiedono la comunicazione con servizi esterni, la logica applicativa utilizza un pattern di prenotazione (reservation pattern). Il microservizio effettua una scrittura condizionata su DynamoDB, inserendo un record con uno stato provvisorio. Successivamente, invoca l’API del provider esterno. In caso di risposta positiva, il sistema aggiorna l’elemento con l’identificativo definitivo; in caso di fallimento della chiamata di rete, l’applicativo esegue un rollback eliminando il record provvisorio e restituendo un codice di errore HTTP al client.

4.3.4 Emulazione delle Risorse AWS tramite LocalStack

Per simulare l’infrastruttura cloud senza richiedere connettività di rete o incorrere in costi di fatturazione, l’ambiente di sviluppo esegue l’applicativo LocalStack [40] all’interno di un container dedicato. Questo strumento espone un singolo endpoint di rete locale in grado di emulare le API di molteplici servizi AWS, tra cui Amazon DynamoDB, Amazon S3 e Amazon SNS.

I microservizi applicativi reindirizzano il traffico verso le risorse simulate decodificando specifiche variabili d’ambiente. Come mostrato nel Listato 4.14, la configurazione inietta l’URL dell’emulatore (AWS_ENDPOINT_URL) e credenziali crittografiche fittizie. Questo pattern di progettazione mantiene inalterata la semantica del codice sorgente, istruendo l’SDK (Boto3) del fornitore cloud senza richiederne la modifica.

Il demone Docker orchestra l’inizializzazione dell’ambiente emulato eseguendo uno script shell (init-aws.sh) montato come volume di sola lettura. Questo script provvede a istanziare le risorse cloud effimere e a popolare le basi di dati con le informazioni necessarie per il collaudo al momento dell’avvio.

Un’operazione fondamentale riguarda la generazione delle tabelle DynamoDB per i servizi backend. Il comando di inizializzazione, esposto nel Listato 4.15, dichiara esplicitamente lo schema delle chiavi primarie e alloca gli Indici Secondari Globali (GSI) necessari per supportare i medesimi pattern di accesso definiti nell’ambiente di produzione.

Lo script assolve a una seconda funzione critica per il collaudo dei worker asincroni (pipeline ETL). Il codice provvede a caricare i file JSON di test all’interno dei bucket S3 emulati, replicando l’esatta gerarchia dei percorsi (raw/) attesa in produzione. Questa pre-inizializzazione dello stato consente di validare la logica di estrazione, la sanificazione e la trasformazione nel formato Parquet operando esclusivamente sulla memoria e sul disco locale.

Questa configurazione architetturale genera un ambiente di sviluppo locale isomorfo all’infrastruttura di destinazione. L’isolamento delle dipendenze garantisce un ciclo di collaudo deterministico e un riscontro immediato su eventuali difetti logici, riducendo il tempo necessario per le iterazioni di sviluppo prima del rilascio in ambiente cloud.

4.4 Automazione del Rilascio e Pipeline GitOps (CI/CD)

Questa sezione illustra la topologia dell’infrastruttura di Continuous Integration e Continuous Delivery (CI/CD) implementata per il ciclo di vita del software. L’analisi procede separando logicamente tre fasi: la compilazione automatizzata e il versionamento semantico (CI), il meccanismo di promozione controllata verso gli ambienti di esecuzione (CD) e, infine, l’imposizione formale delle policy di sicurezza e rollback.

4.4.1 Versionamento Semantico e Compilazione (CI)

L’architettura adotta un modello di distribuzione basato su release. Il processo determina il versionamento semantico analizzando la cronologia dei commit e innesca la compilazione dell’artefatto esclusivamente al momento della generazione effettiva di una nuova release. Il sistema di automazione esegue il job di compilazione e caricamento dell’immagine Docker solo se l’indicatore booleano conferma l’avvenuta creazione della release.

4.4.2 Pipeline GitOps e Promotion Gate (CD)

Al termine della compilazione e del push dell’immagine Docker sul registro Amazon ECR, il sistema interrompe l’esecuzione automatizzata. La distribuzione (deployment) richiede un innesco esplicito tramite l’evento workflow_dispatch, che introduce un promotion gate.

L’azione composita responsabile del caricamento incapsula le interazioni con l’infrastruttura AWS, inclusa la creazione idempotente del repository ECR e la compilazione per architettura ARM64.

4.4.3 Controlli di Sicurezza e Procedure di Rollback

La pipeline integra meccanismi di sicurezza governati direttamente dal codice sorgente. L’immutabilità delle etichette (IMMUTABLE) previene la sovrascrittura accidentale delle release. Inoltre, il sistema applica le policy di accesso (Resource-based policy) solo in caso di discrepanze rilevate tramite jq, mitigando il Configuration Drift.

L’adozione di tag immutabili costituisce il fondamento per le procedure di rollback. Qualora si verifichi una regressione, l’operatore innesca nuovamente il flusso di distribuzione manuale iniettando il tag della versione stabile precedente, forzando il runtime serverless ad avviare i container basati sull’artefatto già validato.

4.5 Implementazione di Service-Forge e Integrazione MCP

L’implementazione del framework Service-Forge adotta una rigorosa separazione delle responsabilità, strutturata su quattro livelli logici contigui come raffigurato in Figura 18. L’interfaccia applicativa espone sia una Command Line Interface (CLI) sia un server Model Context Protocol (MCP). Le richieste in ingresso convergono verso il motore centrale, deputato all’orchestrazione del processo di scaffolding. La generazione effettiva del codice sorgente è delegata a Jinja2 [55]; la scelta di questo motore di templating, nativo per l’ecosistema Python, è motivata dal supporto integrato per costrutti condizionali, iterazioni e meccanismi di ereditarietà tra template base. Infine, il livello di persistenza isola gli effetti collaterali, incapsulando la scrittura fisica dei file e l’inizializzazione del sistema di controllo di versione Git. Questa stratificazione garantisce il riutilizzo totale della logica di base indipendentemente dal canale di interazione prescelto dall’utente.

A livello architetturale, il sistema concretizza la sua logica tramite pattern di progettazione consolidati. La Dependency Injection disaccoppia i componenti per agevolarne il testing unitario. Un pattern Factory istanzia dinamicamente i generatori appropriati in base al profilo di progetto selezionato (es. API sincrona, worker ETL). La separazione tra la generazione dei contenuti testuali e la loro persistenza su disco è mediata da un pattern Observer, mentre l’astrazione Strategy permette di mutare il comportamento di scaffolding in funzione del dominio applicativo.

4.5.1 Sviluppo della Command Line Interface (CLI)

L’interfaccia a riga di comando, sviluppata tramite la libreria Typer [56], guida l’operatore nella composizione interattiva della configurazione di progetto. Il flusso di esecuzione procede sequenzialmente: parte dalla selezione del profilo architetturale e dalla definizione del percorso fisico, per poi richiedere la configurazione dei servizi AWS necessari e dei parametri del runtime serverless. A valle dell’inserimento, il sistema esegue una validazione formale prima di delegare al motore centrale la generazione degli artefatti.

La CLI funge esclusivamente da livello di presentazione. Non contenendo logiche di scaffolding codificate rigidamente, essa raccoglie l’input e lo trasferisce al livello sottostante. Questa delega totale assicura una rigorosa coerenza comportamentale tra l’esecuzione manuale da terminale e l’esecuzione automatizzata tramite assistenti IA.

4.5.2 Esposizione dei tool tramite Model Context Protocol (MCP)

L’integrazione del framework con gli assistenti basati su Large Language Models operanti negli IDE avviene tramite un server conforme al Model Context Protocol, implementato avvalendosi della libreria FastMCP. Il server espone due categorie di astrazioni: risorse in sola lettura per la scoperta dei profili architetturali supportati, e strumenti operativi (Tools) necessari per la configurazione e la generazione del codice sorgente.

Durante la fase di inizializzazione, il server inietta nell’agente conversazionale un set di istruzioni testuali di sistema. Come illustrato nel Listato 4.20, queste direttive vincolano il modello logico a richiedere esplicitamente all’operatore umano i parametri infrastrutturali reali (es. identificativi dei bucket S3 o nomi delle tabelle DynamoDB), prevenendo categoricamente la generazione di codice cloud contenente valori placeholder.

4.5.3 Interazione deterministica con i Large Language Models

Il disaccoppiamento introdotto dall’MCP presenta una sfida architetturale: la comunicazione tra l’LLM e il server locale è intrinsecamente stateless. Per forzare un’interazione deterministica e limitare le allucinazioni del modello, il sistema delega il controllo del flusso al server locale tramite quattro vincoli architetturali: l’imposizione di una sequenza operativa rigorosa, la validazione strutturata dei payload di configurazione tramite Pydantic, l’obbligo di formattare le risposte in formato JSON standardizzato e l’integrazione di una funzionalità di simulazione (dry-run) per ispezionare l’astrazione generata senza alterare il file system.

Per supportare la sequenzialità delle operazioni, il server implementa un registro in memoria che associa a ogni sessione di interazione un identificativo alfanumerico univoco. Il Listato 4.21 dimostra come l’invocazione dello strumento create_session istanzi una struttura dati predefinita contenente le dipendenze AWS e le configurazioni del runtime.

Ogni successiva invocazione di uno strumento di configurazione o generazione richiede il passaggio obbligatorio di tale session_id e modifica esclusivamente la porzione di stato isolata. Questo paradigma operativo riduce le ambiguità contestuali e assicura che il processo di generazione del microservizio rimanga prevedibile e tracciabile, indipendentemente dall’ambiente di sviluppo integrato (IDE) adottato dallo sviluppatore.
